# Architecture Decision Record

Decisions recorded as they were made. Format per assignment §5

## 1. Flask over Django and FastAPI
Date: 2026-09-28
Status: Decided
Context: The app has to run as a single process serving HTML pages, with SQLite underneath and roughly five tables. I needed a Python web framework to build it on.
Decision: Flask, with the standard library's sqlite3 module and Jinja templates. Three third-party dependencies in total (Flask, pytest, pytest-cov).
Alternatives considered: Django, rejected because its ORM, admin interface, auth system and migration framework are built for projects far larger than five tables — I would install all of it and use a fraction. FastAPI, rejected because it is designed for JSON APIs consumed by a separate frontend, and this app renders HTML from the same process, so its main strengths would go unused.
Consequences: No migration tooling, so schema changes mean editing schema.sql and recreating the database file. No admin interface, so every form is hand-written. In exchange the dependency count stays low and the SQL is written directly, which suits a database I designed myself.

## 2. Scoping Ideas and Occasions as independently modularizable domains
Date: 2026-09-29
Status: Decided
Context: The assignment requires two feature domains that could each become a separate service later. Everything in this app relates to a person, so the split had to be drawn by behaviour rather than by entity.
Decision: Ideas owns capture, collections and tagging. Occasions owns dates, recurrence and countdowns. They share only person_id, and Occasions never queries the ideas tables. When the countdown needs an idea count, it calls a function that ideas.py exposes.
Alternatives considered: A People domain separate from Ideas, rejected because People holds almost no logic and the result would be one empty domain and one doing all the work.
Consequences: The seam is a function boundary, so splitting these into services later means replacing a call with a request. The cost is discipline, since the join that would answer the countdown's idea count directly is available and has to be deliberately avoided.
 
## 3. Data model: per-user tags, and where ownership lives
Date: 2026-09-29
Status: Decided
Context: There is no login. Each visitor is a random id stored in a cookie, so every table has to answer whose row it is.
Decision: people and tags carry user_id. ideas and occasions carry only person_id and derive ownership through the join to people. Tags relate to ideas through idea_tags, keyed on the composite (idea_id, tag_id).
Alternatives considered: A global tags table shared across users, rejected because tag names are personal and one user's rename would affect everyone. Storing user_id on ideas as well, rejected because it depends on person_id rather than on the idea itself, which violates third normal form.
Consequences: Ideas queries join through people to check ownership. The composite key means the database rejects a duplicate tag on an idea rather than application code having to check first. Dates are stored as ISO text and recurs_annually as 0 or 1, since SQLite has neither a date nor a boolean type.
 
 ## 4. Testing the pure logic first, database access second
Date: 2026-10-09
Status: Decided
Context: Section 4 asks for coverage of core business logic rather than framework glue or routing, so the first question was which code actually contains rules that could be wrong.
Decision: Tag parsing and date recurrence are tested directly as pure functions. Database access is tested only where it enforces a rule, which is ownership filtering and the upcoming query. Coverage is measured on tagger.py and occasions.py with `pytest --cov=tagger --cov=occasions --cov-report=term-missing`, currently 96% across 28 tests.
Alternatives considered: Testing the Flask routes with a test client, rejected because the routes contain no logic of their own. They read a form, call a domain function and redirect, so a route test would mostly assert that Flask works. Testing people.py, rejected for the same reason: it is an INSERT and a SELECT with no branch that could produce a wrong answer.
Consequences: The two uncovered lines in occasions.py are the leap-year fallback inside the first branch of next_occurrence. The templates and routes are untested, so a broken form or a wrong template variable would not be caught by the suite. Testing the database functions required reloading the modules inside the fixture, because db.py reads DATA_DIR at import time rather than inside get_connection; computing the path per connection would have avoided that and is the cleaner design.
 
## 5. Not building automatic tagging
Date: 2026-10-09
Status: Decided
Context: Tags are typed by hand, so "book" and "books" become separate tags and nothing connects "marvel" to "mcu". Either a keyword dictionary or a language model would close that gap.
Decision: Tags are entered manually, with a datalist of previously used tags as the only assistance.
Alternatives considered: A hardcoded keyword dictionary mapping terms to themes, rejected because it only recognises words chosen in advance and still fails on typos and synonyms. A language model API, rejected because it is non-deterministic, which makes the tagging logic untestable against a coverage target, and because it requires an API key the grader would not have, breaking the clone-and-run requirement in section 7.4.
Consequences: Tag quality depends on the user being consistent, and near-duplicate tags will accumulate. In exchange the tagging logic stays a pure function with no external dependency, which is what makes it the most thoroughly covered module in the project.

## 6. Splitting Ideas and Occasions into two services
Date: 2026-11-20
Status: Decided
Context: In the first version both domains ran in one Flask process. Occasions called a function in ideas.py for the idea count, and its upcoming query joined the people table directly, so both domains depended on the shape of that table. To build, ship and run them separately, each one had to own its data and reach the other only over the network.
Decision: Two services, Ideas and Occasions, each with its own Dockerfile, its own database and its own database login. Ideas owns people, ideas, tags and idea_tags. Occasions owns the occasions table and stores user_id and person_id as plain values, with no foreign key. When Occasions needs a person it calls GET /people/<id> on Ideas over HTTP, forwarding the X-User-Id header and using a 3 second timeout. Ideas decides whether the person belongs to that user, and returns the name and the ideas. If Ideas cannot be reached, reading upcoming occasions still works and returns them marked as degraded, with the name and idea count empty. Creating an occasion returns 503 instead, because the person cannot be verified.
Alternatives considered: One shared database with both services reading the same tables, rejected because it keeps the dependency on the people table that the first version was marked down for, and neither service could change its schema or be deployed on its own. Giving Occasions its own copy of each person's name, rejected because the copy can go stale and would then need syncing, which is more machinery than one call per person.
Consequences: The database can no longer enforce that an occasion points at a real person, so that check happens in code when the occasion is created, and no route deletes people today. Showing upcoming occasions costs one HTTP call per distinct person, which is fine at this size and would need batching with many people. Small pieces of code are duplicated in both services, such as the database module, the header check and CORS, so that each image is complete on its own. In return, each service can be built, tested, deployed and scaled to zero separately, and a failure in one is visible and handled instead of taking both down.

## 7. Numbered SQL migrations applied at startup
Date: 2026-11-22
Status: Decided
Context: The first version created its tables with CREATE TABLE IF NOT EXISTS when the app started, which can build a table but never change one that already holds data. With two databases on Azure SQL and a pipeline that redeploys on every merge, a schema change has to reach a database full of rows without losing any, and the service has to start even when the serverless database is paused and needs a minute to wake up.
Decision: Each service keeps numbered SQL files in its migrations folder and applies them itself at startup, in order, each one once, recording the file name in a schema_migrations table. An applied file is never edited, so every change is a new file. Connections retry with a growing delay for up to a limit, so a paused database delays startup instead of crashing it. Migration 002 adds ideas.priority with a default of 2 and a check that limits it to 1 to 3, which gives every existing idea priority 2, and a test applies the file to a table that already holds a row and checks the row survives. Each service's database login can change the schema of its own database only.
Alternatives considered: Keeping CREATE TABLE IF NOT EXISTS, rejected because it cannot add a column to an existing table. A migration tool such as Alembic or Flyway, rejected because with two services and a handful of changes it adds a dependency and a second description of the schema, while a numbered file and a short runner are enough and easy to explain. Running migrations as a pipeline step, rejected because the pipeline would need network access to the database and a firewall rule for the runner, while the service already has the connection.
Consequences: The runner executes on every start and does nothing when there is nothing new, and CI exercises it against a real SQL Server on every push. If two copies of a service started together they could try the same migration, which cannot happen at one replica but would need a lock if the maximum were raised. A migration that fails stops the service from starting, so the deploy check goes red instead of the app running on a half-changed schema. There are no down migrations, so undoing a change means writing a new one. The retry and the failed-migration paths in db.py are not covered by tests, which is why it sits at 83%.

## 8. Serverless hosting on Azure with Container Apps, free SQL databases and a storage website
Date: 2026-11-22
Status: Decided
Context: The system has to be reachable on the internet, be deployed only by the pipeline, and cost almost nothing while nobody uses it, on a student subscription whose credit is limited. It has two services that need a database each, and a static page that calls both from the browser.
Decision: Each service runs as one Azure Container App on the Consumption plan, in one shared environment, with a minimum of 0 and a maximum of 1 replica and a quarter of a vCPU. It pulls its image, tagged with the commit SHA, from the public GitHub Container Registry. Each service has its own serverless Azure SQL database on the free offer, both on one logical server, and its own database login that can reach only that database. The connection string is stored as a Container App secret and passed to the app as a reference to it, never as plain text. The UI is a folder of static files in an Azure Storage account with static website hosting, and its address is the only origin both services accept. The pipeline signs in with a user-assigned managed identity through OpenID Connect, trusted only for runs on main and holding Contributor on one resource group, so no Azure password exists to leak. Every setting reaches the apps as an environment variable set by the pipeline. The cost model is pay per use throughout. Container Apps bill for the seconds a container runs and have a monthly free grant, the free SQL offer costs nothing, the storage account costs a few cents for the files and requests, the Log Analytics workspace that Azure creates with the environment is free up to 5 GB a month, and the registry and the identity are free. Nothing has a fixed monthly cost.
Alternatives considered: An App Service plan or a virtual machine, rejected because they bill for every hour they are switched on whether or not anyone visits, and the assignment lists always-on compute as out of scope. A provisioned Azure SQL database, rejected for the same reason. Azure Static Web Apps for the UI, not used because this assignment's hosting contract specifies a storage static website, which needs no extra service and is uploaded with the same identity that deploys the apps. A service principal with a stored secret, rejected because IE accounts cannot create one and a stored secret can leak, while the managed identity with a federated credential has nothing to leak.
Consequences: Scaling to zero means the first request after a quiet period starts the container, and Azure can answer it with a 503 after about 30 seconds, so the UI shows a "waking up" notice and retries its reads, and sends each write only once. The free database pauses after 60 minutes idle and takes about a minute to resume, during which connections fail, so db.py retries with a growing delay for up to 90 seconds before giving up, which makes a paused database delay startup instead of crashing it. Every start also checks for pending migrations, and the maximum of one replica is what guarantees that a migration never runs twice at the same moment. A migration that fails stops the service from starting, and the post-deploy check, which retries /health for several minutes and looks for the new commit SHA, then turns the run red. The first deploy failed because GitHub put the repository's numeric IDs in the sign-in token instead of its name, and a second federated credential with that subject fixed it. Both services are public, since the browser calls them, and are protected only by the X-User-Id header and CORS, which is not authentication. At 100 times the traffic several things change. The maximum replica count would have to rise, which breaks the single-replica guarantee, so migrations would need a database lock or a separate job that runs before the new revision. The minimum would become 1 to remove cold starts. The free database would give way to a paid tier with more vCores and no auto-pause. Occasions would batch its person lookups, as ADR-6 already says. A CDN would sit in front of the static files.
